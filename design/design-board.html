UI Specification · v0.1

吾爱Nova浏览器 · 多内核 · 双端

面向 PC 与移动端的一套界面：顶部内核切换是产品的主交互，因此它在视觉上被赋予最高的信息优先级； 三种内核（原生 / 原生桥接 / 兼容层）必须在任何时刻都能被一眼分辨，绝不允许把兼容层画成真内核。 移动端的阅读增强（无图模式 / 自动拼页）把两个开关收进一个底部弹层，底栏只留一个入口， 是「底栏不堆功能」这条规则的直接应用。 本设计稿与 src/renderer/shell.css 共用同一套设计令牌，改这里等于改产品。

02

内核语义的视觉编码

三种运行时模式必须「结构性可辨」——靠颜色 + 形状 + 文案三重编码，而不是只靠一个颜色。
运行时模式视觉编码使用规则示例
原生内核
native		 原生内核
实底圆角胶囊 · 绿		 进程内真实渲染的内核（Chromium/Blink）。地址栏右端徽标用 内核标识色实底 + 反白文字，下拉项的选中底纹与标签条下方指示条同色。 CR
原生桥接
bridge		 原生桥接
实底圆角胶囊 · 蓝		 找到了原生宿主二进制，走独立进程渲染。视觉上与原生内核同等待遇（同样是实底），因为用户拿到的是真内核行为。 原生桥接
兼容层
compat		 兼容层
橙描边 + 橙字		 用 Chromium 渲染但伪造了该内核的 UA / 客户端提示 / 文档模式。地址栏徽标与下拉项都不填实底，转为橙描边 + 橙字； 进入该内核时必须弹出提示条说明降级原因 —— 这一条是硬规则，不允许静默降级。 IE

为什么不能只靠颜色：橙色在浅色底上对 surface-2 的对比度只有 2.1:1，单独用色会在弱视或强光下失效； 橙色描边 + 不填实底 + 下拉项文字标签 + 强制提示条四重冗余，保证任何条件下都能识别「这不是真内核」。

内核信息

Chromium（系统内核）版本 126.0.6478.122 · 随系统更新 当前
本应用不内置浏览器内核。网页由 Android 系统内核 渲染 —— 它是 Chromium 内核， 由系统或 Chrome 提供并自动更新。安装包里没有任何内核二进制（零个 .so）， 这也是它只有 295 KB 的原因。

以前这里是一个可以点的选择器，现在删掉了：只有一档真内核时， 列表里放一枚选项不是选择器，是装饰 —— 它会让用户以为能换内核。
不提供的能力（平台边界）
GeckoView（真 Firefox 内核）：真实存在，但需内置 80–100 MB × ABI，本包没有。

关于

吾爱Nova浏览器
版本 1.1.0 · 渲染由系统内核（Chromium 126.0.6478.122）提供
一个把「省流量、拦广告、自动拼页、嗅探下载」做实的手机浏览器。
它能做什么
· 自动拼页：往上滑自动接上下一页，上限可调
· 无图模式：按网址后缀判断；另有更彻底的「加载图片」总开关
· 广告拦截：内置名单随包发布，可订阅外部规则
· 媒体嗅探：识别页面里的音视频，多线程分片下载
· 书签：地址栏星标一键收藏，底部面板管理、删除、清空
· 篡改猴（用户脚本）：装 .user.js，按 @match 注入页面
· 标签管理、会话恢复、无痕浏览
它做不到什么
· 不内置浏览器内核：真内核最小 80MB，塞进来这个浏览器会变成 100MB 起步
· 广告拦截只按域名：Android 的拦截接口不告诉我们要拦的是图片还是脚本，元素隐藏规则、路径规则在移动版用不了
· 篡改猴不是 Chrome 扩展：系统内核没有扩展宿主，只支持用户脚本，且不支持跨域等特权
· 下载存在应用私有目录：别的应用看不到这些文件，也还不能通过系统分享直接发出去
和桌面端的关系
拼页算法、嗅探名单、拦截规则解析是同一份代码，由 npm run mobile:sync 从桌面端源码生成后同步过来 —— 两边对同一类链接的判断是一致的，不会出现「桌面端拦得了、手机端拦不了」的分裂。
现在到什么程度
尚未在真机或模拟器上验证。全部功能有单元测试兜底，但下载、嗅探、注入这类和系统版本强相关的行为，只有装上真机跑过才算数。已知待办：下载目录未接系统分享。

图标规范 · 星芒 + 轨道环

星芒 + 轨道环。一颗正在被引力捕获的星。源文件在 assets/icon/，npm run icons 一键重建 34 个文件。

构图

品牌渐变　#5B84FF → #3D6BFF → #00B8A2，与 brand / accent 令牌同源。

Android 自适应图标的两层

108×108 画布上只有 66×66 是保证可见的安全区，所以前景层要放大到 ≈64.6 单位 —— 画满 108 会被各家蒙版裁掉星芒的角。 而背景层铺满 108、不描圆角：圆角交给系统蒙版，自己再描一遍， 在方形蒙版机型上会露出双层圆角的毛边。

每张 PNG 都有断言，不是「生成完看一眼」

图层断言为什么
图标层圆角外 alpha ≤ 8 圆形蒙版切不掉的方形毛边。这是自适应图标最容易出的问题。
图标层中心近白 证明星芒真的画上去了，而不是只剩一个渐变底。
背景层满幅不透明 背景层任何透明都会在蒙版边缘露出下层。
背景层中心与右下角色差 ≥ 16 证明渐变真的铺开了。色差为 0 就是纯色填充，渐变没生效。
背景层中心落在品牌蓝色相 B > R 且 B > G。防止渐变方向写反跑出紫色。

注意背景层没有「中心近白」这条。 第一版把它套用到了所有图层，于是报了 6 条假警 —— 背景层本来就没有星芒。 修法是拆成两套断言，不是放宽阈值。

Windows 窗口图标必须给 .ico，不能给 .png

Windows 会按 DPI 与场景（标题栏 / 任务栏 / 资源管理器）自己挑档位， 给一张 PNG 它只会拉伸。所以 main.js 的 BrowserWindow.icon 指向 assets/icon/nova.ico，而那个 .ico 是手工打的包（6 字节头 + 每档 16 字节目录项 + PNG 数据串接）。

设计规则（正反对照）

写清楚是为了让实现和设计稿不跑偏 —— 这几条是评审时最容易吵起来的地方。
议题正解规则反例与后果
内核徽标配色✓ 地址栏右端胶囊用内核标识色实底 + 反白文字，紧邻网址右侧。面积小，薄涂在浅色底上几乎不可辨。 ✕ 用 14% 透明度的内核色薄涂：浅色主题下与 surface-2 同色，用户看不出当前内核。
兼容层标识✓ 橙描边 + 橙字（不填实底）+ 下拉项文字级模式标签 + 进入时强制提示条，四重冗余。 ✕ 只靠颜色区分：对比度 2.1:1，强光与弱视下直接消失，用户以为在用真 IE 内核。
侧栏导航当前项✓ 大行用薄涂 + 强调色描边。行宽面积大，薄涂已经足够，也更克制。 ✕ 大行也用饱和实底：整屏视觉重量失衡，像一排按钮而不是导航。
焦点环✓ 地址栏聚焦 = 白底 + 2px 品牌色描边 + 3px 外发光环。 ✕ 在已填充区域上再画同色描边：焦点完全隐身，键盘用户无法定位。
数字与计数器✓ 拦截计数用 OK 绿，0 或已关闭时转 灰。 ✕ 永远绿色：用户分不清「拦了 138 个」和「拦截已关闭」。
移动端触控✓ 底栏五宫格，主操作（标签）居中凸起，触控目标 ≥ 44 px。 ✕ 把桌面工具栏等比缩小塞进移动端：按钮不足 30 px，误触率飙升。
内核切换入口✓ 桌面：地址栏右端内核徽标，点开即下拉选择（一眼可见 3 个可选 + 各自模式）。移动：底栏按钮 → 底部弹层。 ✕ 在工具栏另起一个分段控件：与地址栏争夺注意力，且让人误以为内核是全局开关而非当前标签页的属性。
✕ 收进菜单二级页：这是产品最核心的能力，藏起来等于没有。
扩展兼容性披露✓ 火狐扩展卡片上直接列出做了哪些清单改动。 ✕ 静默转换后宣称「完全支持火狐扩展」：用户装完才发现 API 缺失，信任崩塌。
内核二进制披露✓ 设置面板里把每个内核摊开写：版本、体积、文件数、PE 校验出的架构与特征符号、 以及还差哪一环（是没下内核，还是没编译宿主）。 ✕ 只显示一个「内核可用」绿勾：用户无法判断真内核到底装了没有。
✕ 用「已支持 Gecko」这种模糊措辞：二进制在 ≠ 能渲染，差一个宿主编译就完全不同。
拦截源分源呈现✓ 三个源各占一张卡片：「源名 + 厂商 + 网络/隐藏/命中 + 各自订阅的文件与条数 + 独立开关」。 用户能一眼看出拦到的是谁拦的，也能单独关掉某一源排查误伤。 ✕ 三个源合并成一个大数字：误杀正常内容时用户无从下手，只能整块关掉拦截。
✕ 让源开关要走三级菜单才够得着：这是排障第一动作，必须从工具栏盾牌一键直达， 且三个开关就摆在该分区自己的卡片上。
设置页信息架构✓ 独立全屏设置页：左侧分组导航 + 右侧内容，把广告拦截 / 扩展 / 书签 / 历史 / 下载 / 内核 / 隐私 全部收进同一处，导航项上挂实时角标（拦截源 3/3、扩展 3、书签 2）。 窄屏时左侧导航降级为顶部横向胶囊条，不缩成一个「汉堡抽屉」。 ✕ 每个功能一个独立抽屉：用户得记住「下载」在菜单里、「拦截」在盾牌里，找不到就以为没这功能。
✕ 设置里摆上点了没反应的开关：宁可写明「本版未实现」，也不要给假控件。
下载进度可视化✓ 一条任务画一条分段进度条，一格 = 一条连接：谁先跑完、哪几段还在补，直接把「用了几个线程」摆在脸上。 服务端不支持 Range 时格数退成 1，并如实标注「单连接（服务端不支持分片）」；从未分片的任务不画假格子。 ✕ 只用一根整条进度：用户看不出引擎到底开了几条连接，多线程优化等于白做，也无从判断是不是悄悄退化了。
✕ 明明退化成单连接却仍显示「8 线程」：宣称的能力和实际行为对不上。
嗅探结果的可信度分层✓ 判定分四级置信度（响应类型精确命中 / video·audio 前缀 / 扩展名 / 通用二进制+扩展名）， 每一条都把「凭什么认定这是媒体」写在行内，把握不足的挂「存疑」而不是冒充确定。 流媒体清单单独标注「拿到的是切片地址表，不是文件」，HLS 分片默认折叠。 ✕ 只按扩展名认：/watch.mp4 这种动态路由实际返回登录页 HTML，会被当成视频列出来。
✕ 所有结果一律当「确定」展示：点进去才发现是个网页，用户一次就不再信这个功能了。
✕ 几百条 HLS 切片平铺在列表里：真正的正片被淹掉，清单等于没有。
无图模式的省流量边界✓ 在请求发出之前就把图片拦掉（onBeforeRequest 里 cancel），省的是真流量； 台账只报条数，明说「给不出省下多少 MB」——被拦的请求压根没有响应头，Content-Length 无从得知。 字体一律不拦（很多站点的界面图标就是字体，拦掉页面直接散架），favicon 走启发式名单放行并把它标明是启发式。 「显示本页图片」是一次性放行，下一跳自动失效。 ✕ 先让图片下完再用 CSS 把它藏起来：一个字节都没省，却打着「省流量」的旗号——这是纯欺骗。
✕ 按平均图片大小估一个「已省 3.2 MB」：数字好看，但是编的。
